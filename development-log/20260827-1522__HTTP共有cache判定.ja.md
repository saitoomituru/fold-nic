## 目的・非目標

- 目的: origin fetchやCAS統合より先に、HTTP responseをpeer共有可能とする最小条件をpure functionで固定する
- 非目標: RFC 9111全範囲、revalidation、heuristic freshness、range cache、private cache暗号化を完成させない

## 入出力・副作用・権限

- 入力: method、request header、status、response header
- 出力: dispositionとreason code
- filesystem副作用: なし
- network: なし
- authority: HTTP共有可否だけを判定し、content安全性や法的権利を判定しない
- secret境界: Authorization／Cookie値を出力・receipt化しない。存在だけを判定する

## `[FACT]` 事実・観測

- Stage 0はGET／HEAD、status 200、明示的`max-age`／`s-maxage`だけを共有候補にする
- `no-store`は他directiveより優先して保存しない
- Cookie／Set-Cookieはpublic指定があってもStage 0ではprivate-onlyへ落とす
- malformed Cache-Controlを共有許可へ変換しない
- 重複したfreshness directiveは値が数値でも共有許可へ変換しない
- `no-cache`はrevalidation未実装のためshared cacheをbypassする
- GitHub ActionsのRust 1.98.0では`Result::map(...).unwrap_or(...)`に`clippy::map_unwrap_or`が追加適用され、local Rust 1.93.0で再現しないfailureになった

## `[INTERPRETATION]` 考察

- RFC上許される最大範囲より意図的に狭く始めることで、unknown responseのP2P共有事故を避けられる
- hash一致やKamii verdictとは別に、HTTP protocol guardが先に共有を拒否できる

## `[HYPOTHESIS]` 次の仮説

- localhost Gatewayはこのpure policyが`SHARE_CACHE`を返したresponseだけをlocal CASへ共有候補として保存できる
